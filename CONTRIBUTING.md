# Как помочь TubeNX

Спасибо, что заглянул. Это неофициальный YouTube-клиент для Nintendo Switch
homebrew: C++17, libnx, libmpv, собственный Material 3 UI. Проект в ранней
альфе — лента и поиск работают, видео на консоли ещё доводится.

Документ короткий: сначала быстрый старт, потом правила, чтобы наши правки не
мешали друг другу.

---

## 1. Быстрый старт

Нужен Linux (или WSL2) и [devkitPro](https://devkitpro.org/) с devkitA64 и
портлибами Switch.

```bash
git clone https://github.com/agafak1337/TubeNX.git
cd TubeNX

# 1. toolchain: ставим один раз, версии — tools/toolchain.md
#    (pacman devkitPro: switch-dev + switch-mpv switch-curl switch-jansson
#     switch-ffmpeg switch-sdl2)

export DEVKITPRO=/opt/devkitpro        # или ~/devkitpro
export DEVKITA64=$DEVKITPRO/devkitA64
export PATH=$DEVKITPRO/tools/bin:$DEVKITA64/bin:$PATH

make doctor        # покажет версии и наличие портлиб
make -j$(nproc)    # → TubeNX.nro
make test-host     # host-тесты, должны быть ЗЕЛЕНО
```

Консоль для разработки **не обязательна**: почти всё проверяется на ПК
(host-тесты и offscreen-рендер экранов).

Подробный разбор первого дня, с ожидаемым выводом каждой команды —
[`docs/onboarding.md`](docs/onboarding.md).

## 2. Что проверять перед каждым PR

```bash
make -j$(nproc)          # release: 0 предупреждений
make -j diag             # диагностическая сборка: 0 предупреждений
make test-host           # ИТОГ: ЗЕЛЕНО
bash tools/preview.sh /tmp/tubenx   # если трогал UI — глазами посмотреть PNG
```

Четыре правила:

1. **Ноль новых предупреждений.** Сейчас их ноль, планку не снижаем.
2. **`make test-host` зелёный.** Если сломал тест — чини тест или код, но не
   отключай проверку.
3. **Один PR — одна тема.** Не смешивай рефакторинг, переименования и фикс.
4. **Ничего не пушим в `main` напрямую.** Только ветка + PR; в `main` мержит
   владелец репозитория.

## 4. Правила, которые нельзя нарушать

- **`design/` — read-only для разработчиков.** Это исходные макеты и токены;
  код под них подгоняем. Меняет `design/` только дизайнер, отдельной веткой и
  по согласованию — см. [`docs/design-guide.md`](docs/design-guide.md).
- **`docs/impl-tz.md` важнее аннотаций.** Если код и ТЗ расходятся — прав ТЗ,
  а расхождение надо описать в PR.
- **Не добавляй зависимости** (библиотеки, портлибы) без обсуждения: сборка
  должна оставаться воспроизводимой по `tools/toolchain.md`.
- **Не коммить секреты и личные данные:** токены, cookie, IP-адреса своих
  машин, серийные номера консолей, пути вида
  `$XDG_RUNTIME_DIR/gvfs/mtp:host=...`. В логах и примерах — плейсхолдеры.
- **Никаких бинарников в git.** `.nro`, `.elf`, логи — только в Releases или
  локально.
- **Прокси и DPI** — инструмент, а не самоцель: не превращай проект в
  «обходчик блокировок» и не обещай в документации того, чего нет.

## 5. Стиль кода

- C++17, без исключений и RTTI (`-fno-exceptions -fno-rtti`), без `std::thread`
  там, где уже есть обёртки из `core/threads.hpp`.
- Отступ — 4 пробела, скобки в стиле Аллмана, пробелы вокруг операторов.
- Комментарии и логи — **по-русски**, по делу: зачем, а не что.
- В начале файла — строка вида `// ui/app.cpp — состояние, навигация, конфиг.`
- Имена: `snake_case` для функций и переменных, `PascalCase` для типов,
  `kSomething` для констант.
- Логи только через `platform::bootLog(...)` с уровнем; не `printf` в UI-потоке.
- Не логируй полные URL: подписанные ссылки YouTube содержат секреты и живут
  часами. В логах — только хост.

## 6. Коммиты и ветки

Формат сообщения:

```
тип(область): короткое описание в императиве

Почему это нужно и что меняется. Если есть номер задачи (DPI-19, PL-06) —
он в заголовке или в теле.
```

Типы: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `diag`
(диагностика/логирование). Области: `ui`, `md3`, `net`, `dpi`, `yt`, `player`,
`core`, `docs`, `build`.

Ветки:

| Ветка | Назначение |
|---|---|
| `main` | публичная страница проекта и стабильное состояние |
| `release/diag` | снимок для тестеров, к нему привязаны Releases |
| `<твоё-имя>/<тема>` | рабочая ветка, PR в `main` |

Релизы и теги ставит только владелец репозитория и только после прогона на
консоли.

## 7. Как тестировать без консоли

- `make test-host` — тема, токены, InnerTube, SOCKS/DPI, сеть, конфиг,
  M3-виджеты, строки, шрифты.
- `bash tools/preview.sh /tmp/tubenx` — offscreen-рендер всех экранов в PNG
  (тот же код UI, что и в NRO). Так ловятся визуальные регрессии.
- Отдельные тесты собираются вручную, например:
  `g++ -std=c++17 -O2 -Isource -Itools tools/test_dpi.cpp source/dpi/dpi.cpp -DTNX_HOST`.

## 8. Как тестировать на консоли

Если есть Switch с Atmosphere/hbmenu:

```bash
bash tools/build.sh          # сборка + проверки
bash tools/deploy.sh         # копирование на SD через MTP + sha256
bash tools/pull-log.sh       # забрать свежий лог в logs/
```

Чек-лист и шаблон отчёта — [`docs/hardware-smoke.md`](docs/hardware-smoke.md).
В отчёте нужны: шаг, время, что на экране, хвост `sd:/switch/TubeNX/logs/*.log`
и строка `start v=… build=…` из начала лога.
