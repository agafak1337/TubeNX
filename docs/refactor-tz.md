## 1. Что такое TubeNX

TubeNX — клиент YouTube для Nintendo Switch, который:

- запускается из **hbmenu** как `.nro` (значит, в NRO должны быть NACP-метаданные
  и иконка);
- не требует аккаунта Google: история и рекомендации хранятся **локально** на SD;
- рисует интерфейс **собственным программным рендерером** в framebuffer libnx,
  без SDL/GPU (Material 3 Expressive, тёмная тема по умолчанию);
- ходит в InnerTube (внутренний API YouTube) без официального API-ключа;
- воспроизводит видео через **libmpv** (`vo=libmpv`, аудио через `hos`/audren);
- обходит DPI-блокировки: локальный **SOCKS5** с фрагментацией TLS ClientHello,
  подмена/верхний регистр SNI и локальный **HTTP-ретранслятор** для плеера.

### 1.1. Что входит в продукт

- Экраны: `Splash`, `Home`, `Search`, `Player`, `Settings`.
- Навигация: геймпад (фокус, D-pad, стик, `A/B/X/Y`, `L/R`, `ZR`), тачскрин,
  экранная клавиатура Switch.
- Лента, поиск с подсказками, продолжение просмотра, локальные рекомендации.
- Настройки: тема, seed-цвет, качество, скорость, сдвиг звука, обход DPI,
  внешний прокси, диагностика, выход.
- История просмотра и лайки — **только локально**.

### 1.2. Чего в продукте нет и не должно появиться

- Входа в Google-аккаунт, подписок, облачной истории, синхронизации.
- Загрузки видео на SD, кэширования полных видеофайлов.
- Комментариев, серверных лайков, уведомлений.
- Рекламы, аналитики, отправки телеметрии.
- Автообновления и установщика: только `.nro` в `sd:/switch/`.

### 1.3. Граница с ТЗ на дизайн (`docs/design-tz.md`)

`docs/design-tz.md` — **отдельное ТЗ, которое уже отдано другому агенту**. Оно
про визуальный язык: макеты экранов, токены, палитру, иконку, композицию,
motion.

Этот документ (`refactor-tz.md`) — **инженерная переделка**. Агент по нему:

- **не придумывает** новый дизайн, не меняет seed, палитру, сетку, типографику
  и композицию экранов «по вкусу»;
- **не делает** новые макеты/HTML/PNG и не перерисовывает иконку;
- **обязан** реализовать в коде то, что уже решено в `design-tz.md` и лежит в
  `design/` (если эти файлы доступны), и починить инженерные проблемы, из-за
  которых дизайн нельзя реализовать: рендерер, масштаб, состояния,
  производительность.

Если в `design-tz.md` чего-то нет — это вопрос к дизайн-агенту и пользователю,
а не повод самому придумывать. Такие места — в `OPEN_QUESTIONS.md`.

**Коротко:** дизайн — чужой участок, код — наш. Мы доводим приложение до
работающего состояния и реализуем уже принятые визуальные решения, но не
проводим второй дизайн-этап.

Пункты `M3-*`, `UX-*`, `RD-09`, `RD-11`, `DOC-05` остаются **в объёме**: это
проверка и реализация уже принятого дизайна в коде, а не придумывание нового.
Их нельзя выкинуть «потому что дизайн делает другой агент».

## 2. Жёсткие ограничения

Их нельзя «обойти архитектурой» — их нужно учитывать в каждом решении.

| Ограничение | Значение | Следствие |
|---|---|---|
| Сервис `ssl` libnx | максимум **4 сессии** (`sslInitialize(1..4)`) | Нельзя держать больше 4 живых TLS-соединений одновременно |
| GPU | нет | Только программный рендер в RGBA8888 |
| Экран | 1280×720 handheld, 1920×1080 dock | Нужен масштаб/сейф-зона, а не «как получится» |
| Память | общая арена приложения | Кэши изображений/глифов должны иметь лимиты |
| Потоки | newlib, стеки по умолчанию малы | Сетевые потоки — 512 КиБ, число потоков ограничено |
| Сеть | Wi-Fi Switch, высокий RTT, потери | Таймауты и retry — часть UX, а не «костыль» |
| DPI | провайдер режет SNI/QUIC/CDN | Обход должен проверяться на живой сети, а не только на ПК |
| hbmenu | NRO без NACP не показывается | `--nacp` и иконка обязательны |
| Аудио | `ao_hos`/audren, буферы | Задержка звука настраивается, «как в mpv по умолчанию» не годится |
| FFmpeg в порте | собран без TLS | Видео качает libcurl через локальный ретранслятор |

**Отдельно про SSL-бюджет.** Это главный архитектурный лимит. Сейчас:

- UI-пул: `kApiHandles = 1`, `kImgHandles = 1` — два постоянных keep-alive
  соединения;
- плеер: до двух сессий (видео + аудио);
- ретранслятор: до 4 слотов, но каждый слот — это отдельный `CURL`, который
  тоже занимает сессию `ssl`.

Любое увеличение пулов без пересчёта бюджета возвращает «клиент молчит» и
`curl 7`. Все новые пулы, ретраи и фоновые загрузки обязаны вписываться в эти
четыре сессии или явно освобождать их.

## 3. Текущее состояние

### 3.1. Что уже работает

- Сборка `TubeNX.nro` (~30,2 МБ) через devkitPro, GCC 15.2.0, `-O2`.
- Запуск из hbmenu: NACP и иконка на месте.
- Интерфейс Material 3, навигация геймпадом/тачем, экранная клавиатура.
- Лента и поиск через InnerTube (при хорошей сети).
- Локальный SOCKS5, SNI-обход, HTTP-ретранслятор, выбор adaptive-потоков.
- Настройки, история, локальные рекомендации, сдвиг звука.
- Host-предпросмотр экранов (`tools/preview.sh`) и проверка контраста токенов.

### 3.2. Что не работает или не подтверждено

| Область | Факт |
|---|---|
| Видео на железе | Сквозной запуск **не подтверждён**: в boot10 нет ни `streams:`, ни `player:` |
| Bootstrap | `GET https://www.youtube.com/ -> 400 (7157 байт)` |
| Лента | `POST /youtubei/v1/browse -> curl 28` на 30 с; скачано 485 268 байт |
| Обложки | все `i.ytimg.com/.../hqdefault.jpg -> 404 (1589 байт)` |
| Канал | тест `speed.cloudflare.com/__down -> 405 (37 байт)` — невалидный тест |
| TLS | `ssl: SetSocketDescriptor rc=0xffffffff` |
| Логи | десятки `ssl: DoHandshake rc=0x1987b` (в boot10 — 59 суммарно) |
| Логи | литерал `+%lld в очереди` вместо числа |
| Плеер | ни одного открытия потока за boot10 |
| Dock | нет обработки смены режима, кадр всегда 1280×720 |
| CI/тесты | отсутствуют |

### 3.3. Ключевое противоречие

На **ПК** тот же код через тот же SOCKS5 даёт:

- `GET https://www.youtube.com/` → `200`, 899 356 байт, ~1,08 с;
- обложки → `200`, 15–21 КБ, 0,36–0,54 с.

На **консоли** — `400`, `404` и таймауты. Значит, проблема не в «алгоритме
обхода» как таковом, а в одном из слоёв, который на ПК отсутствует:

1. сервис `ssl` libnx (рукопожатие, сессии, неблокирующий режим);
2. формат HTTP-запроса, который собирает curl на Switch;
3. тайминги/размеры буферов SOCKS-ретранслятора на консоли;
4. сетевой путь провайдера до конкретного CDN-края.

**Запрещено** «лечить» это отключением проверки сертификата, увеличением всех
таймаутов до 120 с или бесконечными ретраями. Нужна диагностика по слоям.

### 3.4. Главный приоритет

Сначала — **воспроизводимая диагностика сети** (`M0`), потом — **видео на
железе** (`M1`). Всё остальное, включая красоту и CI, вторично, пока видео не
играет.

## 4. Приоритеты, этапы, порядок работ

### 4.1. Приоритеты

- **P0** — без этого работа не принимается: видео на железе, загрузка ленты,
  отсутствие зависаний и «молчащих» соединений.
- **P1** — нужно для беты: стабильность, понятные ошибки, настройки, логи,
  нормальные таймауты, CI.
- **P2** — качество и долг: полировка, рефакторинг, документация, редкие
  сценарии, производительность сверх бюджета.

### 4.2. Этапы

| Этап | Содержание | Выход |
|---|---|---|
| `M0` | Диагностика сети: 400/404/curl 28, TLS, SOCKS, ретранслятор | Отчёт с точной причиной и исправлением |
| `M1` | Видео на железе: open → file-loaded → 60 с → seek → звук | Лог успешного воспроизведения |
| `M2` | Стабильность: retry, отмена, ошибки, память, suspend | 30 минут без падений и зависаний |
| `M3` | Инженерия: CI, тесты, скрипты, воспроизводимая сборка | Зелёный CI + артефакт |
| `M4` | UX/внедрение дизайна: экраны, состояния, dock, доступность | Скриншоты + ручной чек-лист |

`M3` можно вести параллельно, если он не трогает сетевой код. `M4` — только
после `M1`, иначе красивые экраны будут маскировать неработающее видео.

### 4.3. Правило «одна причина — один фикс»

Запрещено смешивать в одном коммите:

- изменение сетевой логики и перерисовку экрана;
- смену таймаутов и рефакторинг парсера;
- «заодно поправил форматирование» во всём файле.

Один коммит — одна проверяемая гипотеза. В сообщении коммита — `ID` пункта
(например, `NET-03: ...`).

### 4.4. Полный объём: делается всё, кроме дизайна

Цель этапа — закрыть **весь** бэклог 5.1–5.15, а не только `P0`. `P0` — это
**порядок**, а не граница объёма. `P1` и `P2` тоже входят в работу.

Единственное исключение — визуальный дизайн из `docs/design-tz.md` (см. 1.3):
его не переделываем, а реализуем в коде.

На финальной сдаче в `manifest.json` должны быть **все 160 ID**. Недопустимый
статус — `not_started`: если пункт не сделан, он должен быть `blocked` с
причиной или `partial` с точным остатком. «Не успел» — это `partial`, а не
отсутствие пункта.

`P2` нельзя выкинуть молча. Если пункт `P2` объективно не нужен — это
обосновывается в `REPORT.md`, а не просто исчезает из манифеста.

### 5.1. Репозиторий, сборка, CI — `RB`

#### `RB-01` · CI-сборка и артефакт · **P1** · M
**Сейчас.** CI нет. Сборка воспроизводится только на машине автора.
**Цель.** GitHub Actions собирает `.nro` на каждый push и PR, кладёт артефакт и
`sha256`, но **не** создаёт релиз.
**Шаги.** 1) Взять официальный devkitPro Docker-образ. 2) Установить портлибы
(`switch-mpv`, `switch-curl`, `switch-jansson`, `switch-ffmpeg`, `switch-sdl2`).
3) `make -j$(nproc)`. 4) Проверить, что `TubeNX.nro` существует и > 1 МБ.
5) Загрузить артефакт + `sha256sum`. 6) Кэшировать devkitPro, но не кэшировать
`build/`.
**Файлы.** `.github/workflows/build.yml`, `Makefile`.
**Приёмка.** Зелёный workflow на PR; артефакт скачивается; в логе видна версия
GCC и список портлиб.

#### `RB-02` · Версия и воспроизводимость · **P2** · S
**Сейчас.** `APP_VERSION := 1.0.0`, `APP_AUTHOR := agfk` захардкожены; в бинарь
не попадает git-sha.
**Цель.** Версия = `git describe --tags --always --dirty`; в лог при старте
пишется `build=<sha> <date>`; сборка воспроизводима.
**Шаги.** 1) Добавить `-DTNX_BUILD_SHA=\"$(shell git rev-parse --short HEAD)\"`.
2) `-ffile-prefix-map=$(CURDIR)=.` для стабильных путей. 3) Убрать дату/время
из бинаря, кроме явного `-DTNX_BUILD_DATE`. 4) Писать `build:` в `bootLog`.
**Файлы.** `Makefile`, `source/main.cpp`, `source/ui/app.cpp`.
**Приёмка.** Два чистых билда дают одинаковый `sha256` (при одинаковом
тулчейне); в логе есть `build:`.

#### `RB-03` · Гигиена предупреждений · **P2** · S
**Сейчас.** Только `-Wall`; часть предупреждений не видна; `-fno-exceptions`,
`-fno-rtti` — осознанно.
**Цель.** `-Wall -Wextra` без новых предупреждений в `source/` (кроме
`third_party`).
**Шаги.** 1) Включить `-Wextra`. 2) Починить реальные предупреждения.
3) Для `third_party` — `-w`. 4) Сохранять `build.log` в CI.
**Файлы.** `Makefile`, `source/**`.
**Приёмка.** CI не падает; в логе 0 предупреждений из `source/`.

#### `RB-04` · Фиксация тулчейна · **P1** · S
**Сейчас.** В README — «поставьте devkitPro», без версий. У автора GCC 15.2.0
и конкретные портлибы.
**Цель.** `Dockerfile`/`tools/toolchain.md` с точными пакетами и версиями;
сборка не зависит от «у меня стоит».
**Шаги.** 1) Зафиксировать базовый образ. 2) Перечислить пакеты
`dkp-pacman -S ...`. 3) Проверить `gcc --version`, `pacman -Q`. 4) Добавить
`make doctor` — печатает версии и наличие библиотек.
**Файлы.** `Dockerfile`, `tools/toolchain.md`, `Makefile`.
**Приёмка.** Чистый контейнер собирает проект без ручных действий.

#### `RB-05` · Порядок в репозитории · **P1** · S
**Сейчас.** В рабочем дереве лежат неотслеживаемые результаты дизайн-агента:
`design/export/`, `design/screens/*.html`, `design/tools/*.mjs`. Они не в
коммите и могут быть потеряны.
**Цель.** Понятная политика: либо дизайн-исходники коммитятся, либо лежат в
`design/` и описаны в README; сборка не зависит от них.
**Шаги.** 1) Проверить, что `design/` не попадает в romfs. 2) Закоммитить
финальные HTML/PNG или добавить в `.gitignore` с пояснением. 3) Убедиться, что
`tools/__pycache__` игнорируется. 4) Не удалять чужие файлы без согласования.
**Файлы.** `.gitignore`, `design/**`, `README.md`.
**Приёмка.** `git status` чистый после сборки; дизайн-файлы не теряются.

#### `RB-06` · Скрипты сборки/деплоя/логов · **P1** · S
**Сейчас.** Деплой и снятие лога — ручные команды с MTP-путём, который меняется.
**Цель.** `tools/build.sh`, `tools/deploy.sh`, `tools/pull-log.sh` с понятными
ошибками и автоопределением SD.
**Шаги.** 1) `build.sh` — export PATH, `make -j`. 2) `deploy.sh` — найти
`mtp:host=*`, проверить `switch/`, скопировать, посчитать sha256.
3) `pull-log.sh` — забрать `TubeNX-boot.log` в `logs/`. 4) Не хранить
пароли/пути в репозитории.
**Файлы.** `tools/*.sh`, `README.md`.
**Приёмка.** Три команды работают на чистой машине; при отсутствии SD —
внятная ошибка.

#### `RB-07` · Тестовые цели в Makefile · **P2** · S
**Сейчас.** Host-тесты (`test_dpi`, `test_innertube`, `preview`) собираются
вручную.
**Цель.** `make test-host`, `make preview`; тесты не требуют консоли.
**Шаги.** 1) Вынести общие флаги. 2) Собрать `tools/host_stubs.cpp` + тесты.
3) `ctest` или простой runner с кодом возврата.
**Файлы.** `Makefile`, `tools/`.
**Приёмка.** `make test-host` возвращает 0; CI вызывает эту цель.

#### `RB-08` · CHANGELOG и теги · **P2** · S
**Сейчас.** Историю видно только по коммитам.
**Цель.** `CHANGELOG.md` в формате Keep a Changelog; теги только вручную,
после приёмки.
**Шаги.** 1) Описать 0.1.0. 2) Правило: запись в CHANGELOG в том же PR.
**Файлы.** `CHANGELOG.md`.
**Приёмка.** CHANGELOG соответствует тегам.

#### `RB-09` · Аудит размера и состава NRO · **P2** · S

#### `NET-01` · Причина `400` на bootstrap `GET /` · **P0** · M
**Сейчас.** `GET https://www.youtube.com/` возвращает `400` и 7157 байт. На ПК
тот же код — `200` и ~899 КБ. `init()` считает это ошибкой, но продолжает с
публичным ключом; лента потом падает.
**Цель.** Понять точную причину и получить `200` (или осознанный fallback без
`/`, см. `YT-01`).
**Шаги.**
1. В диагностической сборке логировать: метод, полный URL, версию HTTP, **все
   отправленные заголовки** (без токенов), `Content-Length`, первые 512 байт
   тела ответа и заголовки ответа.
2. Сравнить с эталонным `curl -v` на ПК через тот же SOCKS5.
3. Проверить гипотезы по очереди:
   - верхний регистр SNI vs `Host` (не путает ли edge виртуальный хост);
   - лишний/двойной `User-Agent` (см. `NET-07`);

   - `Content-Type`/`Origin` от предыдущего запроса на том же easy-хэндле.
4. Сделать минимальный воспроизводимый тест: тот же запрос без прокси, с
   прокси, с `Verify::None`, с `FRESH_CONNECT`, с `HTTP/1.0`.
5. Зафиксировать вывод в `handoff/<agent>/logs/net-400.md`.
**Файлы.** `source/net/http.cpp`, `source/yt/innertube.cpp`, `source/net/sni.cpp`.
**Приёмка.** В логе есть строка с `status=200` для `/` **или** документированный
fallback, который грузит ленту; в отчёте — точная причина, а не «стало
проходить».

#### `NET-02` · `404` на обложках · **P0** · M

#### `NET-03` · Таймаут `browse` и 3 КБ/с · **P0** · L
**Сейчас.** `POST /youtubei/v1/browse` → `curl 28` через 30 с; скачано 485 268
байт; туннель `down=137315` за 44 234 мс ≈ 3 КБ/с. Это не «медленный старт», а
падение пропускной способности.
**Цель.** Лента грузится < 10 с на нормальном Wi-Fi; при плохой сети — внятная
ошибка, а не 30-секундное молчание.
**Шаги.**
1. Разбить замер на фазы: DNS → TCP connect → SOCKS handshake → TLS handshake →

2. Сравнить малое тело (`generate_204`, 1 КБ) и большое (500 КБ): если малое

5. Проверить MTU/фрагментацию: большие TLS-записи могут теряться на PPPoE.
   Добавить тест `curl --limit-rate`/повтор с меньшим `CURLOPT_BUFFERSIZE`.
6. Исключить двойной прокси: `net::proxy()` + `relayViaLocalSocks`.
7. Ввести бюджет: bootstrap 10 с, browse 20 с, изображения 8 с; при превышении —
   отмена и ошибка.

## 6. Протокол сдачи работы (обязателен)

Работа принимается **только** в описанном ниже виде. Если чего-то нет —
пункт считается невыполненным, даже если код «у меня работает».

### 6.1. Ветка и коммиты

- База: `main` на коммите `7e2295b` (или более свежий `main`, если пользователь
  разрешит).
- Рабочая ветка: `refactor/<agent>` (например, `refactor/deepseek`).
- **Запрещено** пушить в `main`, создавать теги, релизы и PR без разрешения.
- Формат коммита: `NET-03: краткое описание` + тело с гипотезой/проверкой.
- Один коммит — один пункт ТЗ (допустимы мелкие сопутствующие правки, но без
  смешивания доменов).
- Не переписывать историю (`rebase -i`, `force-push`) после того, как ветка
  показана пользователю.

### 6.2. Куда складывать результат

Всё складывается в репозиторий в каталог:

```
handoff/<agent>/
├── REPORT.md              # главный отчёт (шаблон ниже)
├── manifest.json          # машиночитаемый статус по каждому ID
├── BUILD.md               # как собрать именно этот результат
├── OPEN_QUESTIONS.md      # что не удалось проверить / нужны решения
├── patches/               # git format-patch относительно базы
│   ├── 0001-NET-06-....patch
│   └── ...
├── logs/                  # сырые логи, не скриншоты текста
│   ├── host-build.log
│   ├── host-tests.log
│   ├── hardware-boot-01.log
│   └── net-400.md         # разбор конкретной проблемы
├── screenshots/           # PNG, 1280×720 или 1920×1080
│   ├── 01-home.png
│   ├── 02-player.png
│   └── ...
├── artifacts/             # опционально: nro + sha256 (если разрешено)
│   └── TubeNX.nro.sha256
└── SHA256SUMS             # хеши всех файлов в handoff/
```

Дополнительно, **вне репозитория** (в `/tmp` или на рабочем столе):

```
handoff-<agent>.tar.gz
handoff-<agent>.tar.gz.sha256
```

Архив должен содержать только `handoff/<agent>/` (без `.git`, без `build/`,
без 30-МБ NRO, если пользователь не просил иначе).

### 6.5. `BUILD.md`

Минимум:

- точная команда сборки;
- версии devkitPro/портлиб;
- как запустить host-тесты;
- как развернуть на SD;
- как снять лог;
- известные особенности (например, «нужен VPN для сборки»).

### 6.6. Доказательства

Принимаются только:

- **сырой лог** с консоли (`TubeNX-boot.log`), а не пересказ;
- **PNG-скриншот** экрана (не фото телефона, если можно снять скриншот);
- **команда + вывод** для host-теста;
- **diff/патч** для изменений.

Не принимаются:

- «проверил, работает»;
- скриншот, на котором не видно состояния;
- лог, обрезанный до одной удачной строки;
- изменение, которое нельзя собрать из патчей.

### 6.7. Если нет доступа к консоли

Это допустимо, но тогда:

- `manifest.json` честно помечает `blocked` всё, что требует железа;
- в `OPEN_QUESTIONS.md` — что именно нужно проверить и какая гипотеза;
- в `patches/` — изменения, которые можно собрать и проверить на ПК;
- **нельзя** писать «видео работает», если оно не проверено.

### 6.8. Что запрещено при сдаче

- Пушить в `main`, создавать релизы/теги.
- Коммитить `build/`, `*.nro`, `*.elf`, `*.nacp`, логи > 5 МБ.
- Добавлять Claude/DeepSeek в README или исходники как авторов.
- Менять `CONTRIBUTORS.md` без просьбы пользователя.
- Удалять чужие неотслеживаемые файлы (`design/`).
- «Чинить» сеть отключением TLS-проверки без явного флага и предупреждения.
- Оставлять в коде закомментированные простыни и `TODO` без ID.

## 8. Как пользователь передаёт результат на ревью

Пользователь присылает:

1. ветку/коммит или `handoff-<agent>.tar.gz`;
2. `sha256` архива;
3. одну строку: «что должно было заработать» и «что вызывает сомнения».

Проверка со стороны ревью:

1. Распаковать, проверить `SHA256SUMS`.
2. Применить патчи на чистую копию `main` (или взять ветку).
3. Собрать `make -j4`.
4. Запустить `make test-host`.
5. Сверить `manifest.json` с `REPORT.md` и фактическими файлами.
6. Проверить ключевые диффы: сеть, плеер, конфиг.
7. Если есть доступ к консоли — прогнать smoke-чек-лист.
8. Только после этого — merge в `main` и push.

**Критерий отказа:** хотя бы один `done` без доказательства, сборка не
воспроизводится, или в логах есть признаки отключённой TLS-проверки без
предупреждения.

### 8.1. Что делает принимающая сторона (ассистент)

После получения результата:

1. **Фиксирует точку входа:** ветка + коммит + `sha256` архива. Если архив не
   совпадает по хешу — работа не рассматривается.
2. **Проверяет целостность:** `SHA256SUMS`, наличие `manifest.json`,
   `REPORT.md`, `BUILD.md`, `OPEN_QUESTIONS.md`, `patches/`.
3. **Применяет патчи** на чистую копию `main` в отдельный worktree
   (`review/<agent>`). Если патчи не применяются — отказ.
4. **Собирает** `make -j4` и сравнивает `sha256` NRO с заявленным (допустимо
   расхождение из-за тулчейна, но оно должно быть объяснено).
5. **Запускает** `make test-host`; при наличии — host-тесты из `TEST-*`.
6. **Сверяет** `manifest.json` с `REPORT.md`: каждый `done` имеет `evidence`,
   каждый `partial`/`blocked` — причину.
7. **Смотрит диффы** в порядке риска: `net/http.cpp`, `dpi/dpi.cpp`,
   `yt/innertube.cpp`, `player/player.cpp`, `ui/app.cpp`. Ищет:
   - отключение TLS-проверки без флага;
   - бесконечные ретраи/таймауты;
   - новые глобальные мутации под потоками;
   - утечки/циклы владения;
   - логирование токенов.
8. **Проверяет на консоли** (если доступна): smoke-чек-лист 9.3, лог по
   маркерам 9.4.
9. **Выносит вердикт по каждому ID:** `принято` / `принято с замечаниями` /
   `отклонено`, с одной строкой причины.
10. **Публикует:** merge в `main` (или fast-forward, если история линейная),
    push, обновление `README.md` (статус) и `CHANGELOG.md`. Релизы/теги — только
    по отдельной просьбе пользователя.
11. **Отвечает пользователю:** короткий итог, ссылка на коммит, список
    отклонённых пунктов и что нужно доделать.

### 8.2. Если результат частичный

Это нормально, если честно оформлено. Принимающая сторона:

- мержит только принятые пункты (или всю ветку, если конфликтов нет);
- оставляет `OPEN_QUESTIONS.md` в репозитории;
- создаёт список follow-up задач с теми же ID;
- не выдаёт частичный результат за «релиз».

### 8.3. Формат ответа пользователю

```markdown
## Итог ревью <agent>

Принято: N из M пунктов.
Коммит: <sha> (ветка main)

### Принято
- NET-06, NET-07, ...

### Принято с замечаниями
- NET-03 — скорость выросла до X, но на плохой сети всё ещё Y; follow-up.

### Отклонено
- PLR-01 — нет лога `file-loaded`, только скриншот.

### Что дальше
1. ...
2. ...
```

### 9.2. Образец лога boot10 (сокращённо)

```
http: GET https://www.youtube.com/ -> 400 (7157 байт)
http: POST https://www.youtube.com/youtubei/v1/browse -> curl 28: Timeout was reached (485268 байт)
http: GET https://i.ytimg.com/vi/.../hqdefault.jpg -> 404 (1589 байт)
http: GET https://speed.cloudflare.com/__down -> 405 (37 байт)
ssl: SetSocketDescriptor rc=0xffffffff
ssl: DoHandshake rc=0x1987b
http: ... +%lld в очереди ...
```

Что это значит:

- `400` — сервер принял запрос, но счёл его некорректным; смотреть заголовки.
- `curl 28` — таймаут; смотреть фазы и скорость.
- `404` на обложке — CDN не нашёл объект; смотреть URL/качество.
- `405` на `__down` — неверный метод теста, не проблема сети.
- `rc=0xffffffff` — вероятный `-1`; смотреть `errno`.
- `0x1987b` — `SSL_ERR_WOULD_BLOCK`, нормальное ожидание, не ошибка.
- `+%lld` — баг форматирования.

### 9.3. Smoke-чек-лист на консоли

1. Чистый `config.ini` (или удалить).
2. Запуск из hbmenu → Splash → Home.
3. Home: 4 колонки, обложки, скролл.
4. Поиск: ввод, подсказки, результаты.
5. Видео: открыть, 60 с, пауза, seek +30/−30, звук.
6. Настройки: тема, качество, сдвиг звука.
7. Выключить Wi-Fi → ошибка через ≤ 10 с, «Повторить».
8. Включить Wi-Fi → лента грузится.
9. Сон 30 с → пробуждение → видео.
10. Dock ↔ handheld.
11. Выход → hbmenu.
12. Снять лог, проверить маркеры из 7.1–7.2.

```bash
# сборка
export DEVKITPRO=/opt/devkitpro
export PATH=$DEVKITPRO/tools/bin:$DEVKITPRO/devkitA64/bin:$PATH
make -j4

# хост-тесты
make test-host

# деплой (путь MTP меняется)
M="$XDG_RUNTIME_DIR/gvfs/mtp:host=-_DBI_<серийный-номер>/1: SD Card"
cp -f TubeNX.nro "$M/switch/TubeNX.nro"

# лог

# хеши
sha256sum TubeNX.nro > TubeNX.nro.sha256
```

### 9.6. Словарь

- **InnerTube** — внутренний API YouTube, который использует веб-клиент.
- **itag** — числовой идентификатор формата потока (136 = 720p AVC video,
  140 = AAC audio, 18 = muxed 360p).
- **SNI** — имя хоста в TLS ClientHello; DPI режет по нему.
- **SOCKS5h** — SOCKS5 с разрешением имени на стороне прокси.
- **Ретранслятор** — локальный HTTP-сервер, который качает upstream через
  libcurl и отдаёт mpv по `http://127.0.0.1:8899/u?u=...`.
- **SSL-сессия** — слот сервиса `ssl` libnx; всего 4.
- **NACP** — метаданные NRO для hbmenu.

## 10. Итог: что считать «переделкой всего проекта»

Не «переписать всё» и не «сделать только P0». Нужно закрыть **все** пункты
разделов 5.1–5.15, кроме визуального дизайна из `docs/design-tz.md` (его
реализуем в коде, но не придумываем заново).

Порядок работы:

1. `NET-01`, `NET-02`, `NET-03`, `NET-04`, `NET-14`, `DPI-01`, `DPI-07`,
   `YT-01`, `YT-03`, `YT-04`, `YT-07`, `PLR-01`, `PLR-02`, `PLR-07`,
   `CFG-01`, `LOG-06`, `SEC-01`, `SEC-03`, `SEC-05`, `DOC-04` — `P0`.
2. Все остальные `P1`.
3. Все `P2`.
4. Если пункт объективно невозможно закрыть — `blocked` с причиной и планом,
   а не `not_started`.

Сдача — только когда в `manifest.json` есть **все 160 ID** со статусами
`done`/`partial`/`blocked`/`skipped`. `not_started` не допускается.

**Критерий «всё»:** пользователь может запустить приложение на консоли,
увидеть ленту, открыть видео, посмотреть 60 секунд со звуком, перемотать,
выйти и зайти снова — и в логе нет ни одной известной ошибки из раздела 3.2.
Плюс: CI зелёный, host-тесты проходят, `handoff/<agent>/` заполнен, README
честен, дизайн не переделан, а реализован.
