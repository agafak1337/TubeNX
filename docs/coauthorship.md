# Соавторство в TubeNX

Как получить доступ к репозиторию, что он даёт, чего от вас ждут и как выйти
без обид. Документ для человека, который хочет помогать регулярно, а не
прислать один случайный патч.

Одиночные PR из форка тоже приветствуются — для них доступ к репозиторию не
нужен, см. [`CONTRIBUTING.md`](../CONTRIBUTING.md).

---

## 1. Кто такой соавтор

Соавтор — это участник с **правом записи** в репозиторий и закреплённой зоной
ответственности. Это не передача проекта и не работа по найму.

Что соавторство **даёт**:

- право создавать ветки прямо в репозитории и открывать PR;
- право ревьюить PR других участников;
- запись в `CONTRIBUTORS.md` с ролью и зоной;
- участие в решениях по своей зоне (UI, сеть, дизайн, тесты).

Чего оно **не даёт**:

- прав на товарный знак, название и релизы — они остаются у владельца;
- доступа к платежам, секретам, аккаунтам и инфраструктуре;
- обязательства платить или выполнять работу в срок;
- права мержить в `main` и ставить теги без согласования (это делает
  владелец или maintainer).

Код остаётся под лицензией MIT: авторские права на свои изменения сохраняются
у автора, проект может распространять их на условиях MIT. CLA не требуется.

---

## 2. Роли

| Роль | Доступ | Что может |
|---|---|---|
| **Contributor** | нет (PR из форка) | предлагать патчи, issues, документацию |
| **Collaborator** | `write` | ветки, PR, ревью, labels в своей зоне |
| **Maintainer** | `maintain` | мерж в `main`, порядок в issues, релизные ветки |
| **Owner** | `admin` | всё, включая настройки и теги |

Новому человеку обычно дают **Collaborator (`write`)**. Повышение до
maintainer — отдельное решение владельца после нескольких принятых PR.

## 3. Как получить доступ

### Со стороны владельца

Через веб:

1. GitHub → репозиторий → **Settings** → **Collaborators**.
2. **Add people** → GitHub-username → роль **Write** → отправить приглашение.

Или через `gh` (нужен токен с правами администратора репозитория):

```bash
gh api -X PUT repos/agafak1337/TubeNX/collaborators/<username> \
  -f permission=push
```

`push` — это и есть роль Write. Не выдавайте `admin`, если человеку не нужны
настройки репозитория.

Проверить, кто уже есть:

```bash
gh api repos/agafak1337/TubeNX/collaborators \
  --jq '.[] | [.login, .permissions.push, .permissions.admin] | @tsv'
```

### Со стороны приглашённого

1. Принять приглашение: письмо от GitHub или
   `https://github.com/agafak1337/TubeNX/invitations`.
2. Включить **двухфакторную аутентификацию** — без неё GitHub не даст доступ
   к приватным действиям, а для публичного репозитория это просто гигиена.
3. Настроить git:

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "you@example.com"
```

Лучше использовать тот же email, что привязан к GitHub, иначе коммиты не
свяжутся с профилем.

4. Добавить SSH-ключ (Settings → SSH and GPG keys) или использовать
   fine-grained PAT. Токен — только в менеджере паролей, не в файлах
   репозитория и не в переписке.
5. Проверить доступ:

```bash
git clone git@github.com:agafak1337/TubeNX.git
cd TubeNX
git switch -c имя/первая-задача
```

Если клонирование по SSH не настроено, используйте HTTPS и PAT.

## 4. Первый день после приглашения

```bash
cd TubeNX
make doctor          # toolchain и портлибы
make -j$(nproc)      # 0 предупреждений
make test-host       # == ИТОГ: ЗЕЛЕНО ==
bash tools/preview.sh /tmp/tubenx
```

Подробный разбор — [`docs/onboarding.md`](onboarding.md). Задачи — в
[`docs/tasks.md`](tasks.md).

Перед первой правкой напишите, какую задачу берёте: это дешевле, чем двоим
делать одно и то же.

## 5. Правила работы

1. **В `main` напрямую не пушим.** Только ветка + Pull Request.
2. **Один PR — одна тема.** Рефакторинг, переименования и фикс — отдельно.
3. **Ветка живёт недолго.** Если задача большая — draft PR и промежуточные
   коммиты, но не месяц в стороне.
4. **Не force-push в чужую ветку.** Свою — можно, если PR ещё в draft и вы
   предупредили ревьюера.
5. **Проверки обязательны:** `make -j` (0 предупреждений), `make diag`
   (0 предупреждений), `make test-host` (ЗЕЛЕНО). Для UI —
   `tools/preview.sh` и глазами по PNG.
6. **Секреты и личные данные не коммитим:** токены, cookie, IP, серийники,
   пути со своего компьютера, полные подписанные ссылки на видео.
7. **`design/` — зона дизайнера.** Разработчик не правит макеты; дизайнер не
   правит `source/`. Как менять дизайн — [`docs/design-guide.md`](design-guide.md).
8. **Спорные решения — в issue, а не в споре в PR.** Если ТЗ и код расходятся,
   прав [`docs/impl-tz.md`](impl-tz.md), а расхождение описывается в PR.

Ревью: один одобряющий для обычной правки, владелец — для изменений в
`main.cpp`, `platform.hpp`, `Makefile`, релизной ветке и тегах. Если ревьюер
молчит больше двух дней — вежливо напомните, а не мержьте сами.

## 6. Зоны ответственности

| Зона | Файлы | Кто |
|---|---|---|
| UI / M3 | `source/ui/`, `source/md3/`, `source/core/` | участник 1 |
| Сеть / плеер | `source/net/`, `source/dpi/`, `source/yt/`, `source/player/` | участник 2 |
| Дизайн | `design/` | дизайнер |
| Документация | `docs/`, `README.md`, `CONTRIBUTING.md` | все, по согласованию |
| Общее | `source/main.cpp`, `source/platform.hpp`, `Makefile`, `.github/*` | владелец / по согласованию |

Зона — не запрет помогать, а способ не конфликтовать в одном файле. Если
задача требует файла из чужой зоны, сначала договоритесь.

## 7. Кредит и `CONTRIBUTORS.md`

После первого принятого PR добавьте себя (или попросите владельца) в
`CONTRIBUTORS.md`:

```markdown
- **@username** — UI/M3: экраны, виджеты; с 2026-11.
```

Правила:

- только публичный handle, без телефонов, адресов и личных email;
- роль и зона — честно, без «ведущий архитектор» после одного PR;
- если человек ушёл — запись остаётся, доступ снимается.

Пользовательские изменения также попадают в `CHANGELOG.md` (раздел
`Unreleased`). Внутренние рефакторинги — по желанию.

## 8. Безопасность и приватность

- **Не публикуйте логи с личными данными.** Подписанные ссылки на видео
  живут часами и содержат секреты; в issue — только хост и код ошибки.
- **Не выкладывайте скриншоты с серийным номером консоли, IP и именем Wi-Fi.**
- **Уязвимость нашли — не в публичный issue.** Используйте GitHub →
  Security → Report a vulnerability (если включено) или напишите владельцу
  лично. Дождитесь ответа до публикации.
- **Чужой токен/ключ нашли в коде — сразу владельцу**, не коммитьте его
  обратно и не используйте.
- **Не добавляйте зависимости** без обсуждения: сборка должна оставаться
  воспроизводимой по `tools/toolchain.md`.

---

## 9. Как выйти

- Скажите владельцу, что уходите; доступ снимается, запись в
  `CONTRIBUTORS.md` остаётся.
- Ваши PR и коммиты никуда не исчезают.
- Если нужен перерыв — просто перестаньте брать задачи, доступ можно не
  снимать.

Владелец может снять доступ досрочно за: секреты в репозитории, агрессию,
игнорирование правил безопасности или порчу чужой работы. Это не «бан на
проект» — форк и PR из него остаются доступны.

## 10. Чек-лист владельца при приглашении

- [ ] Человек знает, в какую зону идёт, и прочитал `CONTRIBUTING.md`.
- [ ] Выдана роль **Write**, не Admin.
- [ ] Приглашённый включил 2FA.
- [ ] В `CONTRIBUTORS.md` добавлена строка (после первого PR).
- [ ] В issue/чате сказано, какие задачи свободны.
- [ ] Если включаете защиту `main` — «Require a pull request before merging»
      и «Require status checks» (когда появится CI).
