## 0. Как пользоваться этим документом

Это задание на **внутреннюю часть** продукта: сеть, DPI, плеер, конфиг,

Дизайн уже сдан и **не переделывается**. Источник визуальной истины —

5. задаёт требования к конфигу, логам, сборке, тестам (§10–§13);
6. задаёт **протокол сдачи на ревью** (§15);
7. перечисляет запреты и Definition of Done (§16–§17).

Порядок чтения:

1. §1–§3 — что делаем, что уже есть, что сломано.
2. §4 — обязательные решения. Их нельзя пересматривать.

**Граница объёма.** Внутренняя инженерия делается **полностью**: все 160

## 1. Задача и границы

### 1.1. Что делаем

- Довести до рабочего состояния на реальной консоли: лента, поиск, обложки,
  выбор потоков, видео 720p со звуком, seek, пауза, выход.
- Реализовать в коде **ровно тот интерфейс**, который сдан в `design/`:
  сетку, типографику, компоненты, состояния, фокус, dock/handheld.
- Починить сеть: `400` на bootstrap, `404` на обложках, таймаут `browse`,
  3 КБ/с через туннель, флуд TLS-логов.
- Сделать конфиг и историю надёжными: атомарная запись, схема, миграции,
  валидация, очистка.
- Ввести CI, host-сборку и тесты; сделать логи пригодными для диагностики.
- Сдать результат по протоколу §15 в `handoff/<agent>/`.

### 1.2. Что не делаем

- **Не переделываем дизайн.** Никаких новых экранов, цветов, отступов «по вкусу».
  Любое расхождение с макетом — это баг кода, а не повод менять макет.
- Не добавляем аккаунт, вход, подписки, облачную историю, рекомендации с сервера.
- Не добавляем рекламу, аналитику, телеметрию, автообновление.
- Не трогаем `design/` (кроме чтения). Если макет объективно нереализуем —
  вопрос в `OPEN_QUESTIONS.md`, а не тихая правка макета.
- Не упоминаем Claude и DeepSeek в `README.md` и нигде, кроме
  `CONTRIBUTORS.md`.
- Не пушим в `main`, не создаём теги, релизы и PR без разрешения.

### 1.3. Критерий успеха

На реальной консоли, на домашнем Wi-Fi с включённым DPI-обходом:

1. Холодный запуск → Splash → Home с лентой **без ручных действий**.
2. Тап по видео → `streams:` в логе → видео 720p + AAC звук → 60 секунд
   непрерывного воспроизведения → пауза → seek ±30 с → выход → повторный вход.
3. Обложки грузятся (≥ 90 %), битые заменяются placeholder'ом.
4. Лог читается человеком: нет `%lld`, нет флуда, каждая ошибка имеет код и фазу.
5. Интерфейс совпадает с `design/png/` на всех проверяемых кадрах.

## 3. Текущее состояние (проверено, не гипотезы)

### 3.1. Что уже работает

- Сборка `TubeNX.nro` (~30,2 МБ), запуск из hbmenu, NACP с иконкой и названием.
- Программный рендерер, шрифты Google Sans с кириллицей, Material Symbols.
- Навигация геймпадом и тачем, Splash/Home/Search/Player/Settings.
- InnerTube: лента и поиск на публичных клиентах, `ANDROID_VR 1.62.27` и
  `ANDROID 20.10.38`, bootstrap-ключ.
- Локальный SOCKS5 с фрагментацией ClientHello, подмена SNI, ретранслятор
  `http://127.0.0.1:8899/u?u=…`, Range, повторные попытки.
- Плеер: libmpv (`vo=libmpv`, `ao=audren,hos,sdl,null`), адаптивный выбор
  (720p itag 136 + AAC 140), muxed 18 как fallback, seek, задержка звука.

### 3.2. Что не работает или не подтверждено

| # | Факт | Где видно |
|---|---|---|
| 1 | Видео на железе **не подтверждено**: в boot10 нет `streams:` и `player:` | лог boot10 |
| 2 | `GET https://www.youtube.com/` → `400`, 7157 байт | лог |
| 3 | `POST /youtubei/v1/browse` → `curl 28` на 30 с; 485268 байт; туннель скачал 137315 за 44234 мс ≈ 3 КБ/с | лог |
| 4 | Все `i.ytimg.com/.../hqdefault.jpg` → `404`, 1589 байт | лог |
| 5 | `ssl: SetSocketDescriptor rc=0xffffffff` логируется как ошибка | лог |
| 6 | `ssl: DoHandshake rc=0x1987b` (`SSL_ERR_WOULD_BLOCK`) флудит лог | лог |
| 7 | Литерал `+%lld в очереди` попадает в лог | `source/net/http.cpp` |
| 8 | На ПК тот же код: `/` → `200` / 899356 байт / 1,08 с, обложки `200` / 15–21 КБ | host-тест |
| 9 | В логе boot10: 0 × `curl 7`, 0 × «клиент молчит», 0 × «все слоты»; `tube: v3 fix` присутствует | лог |

Вывод: проблема не в «провайдер вообще всё блокирует», а в различии поведения
консоли и ПК на уровне TLS/потока/заголовков. Диагностика — §7.5.

### 3.3. Факты платформы, которые нельзя игнорировать

- Сервис `ssl` в libnx держит **4 сессии** одновременно. Каждое живое
  keep-alive HTTPS-соединение занимает одну. Плееру нужны 2, интерфейсу — 2.
- `socketSslConnectionSetSocketDescriptor()` возвращает `int`; `0xffffffff` —
  это, почти наверняка, `-1`, а не код ошибки libnx.
- `SSL_ERR_WOULD_BLOCK` (`0x1987b`) при неблокирующем handshake — **нормальное**
  состояние опроса, а не ошибка.
- framebuffer сейчас всегда `1280×720`, два буфера с fallback на один;
  dock-режим определяется (`i.docked`), но раскладка от него не зависит.
- Кадр рисуется в кэшируемую память и копируется в framebuffer один раз за кадр.

### 3.4. Главный дефект

Не «медленный интернет», а **незавершённый TLS/HTTP-обмен на консоли**:
`400` на bootstrap, `404` на CDN обложек и `3 КБ/с` через SOCKS при том, что
на ПК тот же код работает. Пока это не закрыто, остальное не проверяемо.
Поэтому `NET-01..NET-03` и `DPI-01..DPI-05` идут первыми.

## 5. Контракт «дизайн → код»

### 5.1. Модель кадра и режимы

- Логический канвас: **1280×720**. Все координаты ниже — в логических px.
- Handheld: framebuffer 1280×720, поля 24, safe area нет.
- Dock: framebuffer **1920×1080**, канвас 1280×720, глобальный масштаб **1,5**;
  safe area 64/36 в логических px (96/54 физических). Текст растрируется
  в физическом размере (кэш глифов по px), а не растягивается.
- Переключение режима — по `AppletHookType_OnOperationModeChanged`, без
  перезапуска приложения; пересоздание окна/framebuffer, сохранение состояния.
- Fallback: если 1920×1080 недоступен — 1280×720 с апскейлом композитора,
  в лог `display: dock fallback 1280x720`.
- Все хит-тесты — в логических координатах; масштаб применяется на уровне
  канваса, а не в каждом экране.
- Канвас получает `setScale(s)` и `safeInsets`; экраны не знают про dock,
  они читают `ui::Layout` (см. 5.3).

### 5.2. Токены темы

**Seed по умолчанию:** `0xFFC3002F` (`#C3002F`, «красный»).
Палитра из `tokens.json`:

| id | Имя | Seed |
|---|---|---|
| `red` | Красный (по умолчанию) | `#FFC3002F` |
| `blue` | Синий | `#FF1A73E8` |
| `green` | Зелёный | `#FF1E8E3E` |
| `purple` | Фиолетовый | `#FF7E57C2` |
| `orange` | Оранжевый | `#FFE8710A` |
| `pink` | Розовый | `#FFD81B60` |

Требования:

1. `Config::seed` = `0xFFC3002F`; `seedList` в `screens.cpp` заменяется на
   таблицу выше (id, имя, seed).
2. `Theme::make()` использует **`Typography::standard()`** с исправленными
   значениями; `switchUi()` (+2 px) **удаляется** — масштаб dock даёт
   физический кегль, а не логический.
3. Все 37 ролей в dark и light совпадают с `design/tokens.json` (допуск
   ΔE00 ≤ 2,0; тест `TEST-03`).
4. `Shapes`: `none 0`, `extraSmall 4`, `small 8`, `medium 12`, `large 16`,
   `largeIncreased 20`, `extraLarge 28`, `full 999`, `badge 6`.
5. State layers: hover 0.08, focus 0.10, pressed 0.10, dragged 0.16,
   disabled content 0.38, disabled container 0.12.
6. Elevation — только всплывающие поверхности (menu, dialog, snackbar,
   elevated). Карточки в списке — тональная поверхность + outline, без тени.

**Движение:** short 150 мс, medium 250 мс, long 400 мс; easing

### 5.3. Общая модель раскладки

Ввести структуру (имя любое, смысл фиксирован):

```
Layout {
  W, H            // 1280, 720
  scale           // 1.0 handheld, 1.5 dock
  marginX         // 24 handheld, 64 dock
  topOffset       // 0 handheld, 24 dock
  safeTop/Bottom  // 0/0 handheld, 36/36 dock
  contentBottom   // 632 handheld, 636 dock
  gridCols        // 4
  cardW           // 296 handheld, 276 dock
  cardGap         // 16
  cardThumbH      // 166 handheld, 155 dock
  cardH           // 256 handheld, 245 dock
}
```

Правила:

- `cardThumbH = floor(cardW * 9 / 16)`, `cardH = cardThumbH + 90`.
- Никаких `if (docked)` внутри экранов — только поля `Layout`.
- Все горизонтальные ряды начинаются с `marginX` и заканчиваются
  `W − marginX`.
- Интерактивные элементы dock — внутри `[64, 64] … [1216, 684]`.
- Исключение `Р-09`: настройки начинаются с x=56 (на 8 px левее номинальной
  safe area) — так в утверждённом макете `settings-top`/`tv-settings`.

### 5.4. Splash

Кадры: `splash-checking`, `splash-ready`, `splash-offline`.

- Фон `surface`, по центру: марка 96×96 (squircle, `primaryContainer`,

  ниже 8 — «YouTube для Nintendo Switch» `bodyMedium` `onSurfaceVariant`.
- Ниже 48 — индикатор: спиннер 22 + текст `bodyMedium`:

## 7. Сеть: целевая архитектура и диагностика

### 7.1. Целевая схема

```
UI / InnerTube / картинки
    └─ libcurl → socks5h://127.0.0.1:<port> (локальный SOCKS5 с фрагментацией)
         └─ прямое TCP к цели, ClientHello фрагментами, SNI-подмена

Плеер (libmpv)
    └─ http://127.0.0.1:<relay>/u?u=<urlencoded>
         └─ ретранслятор: Range, keep-alive, 4 слота, обратно через SOCKS
```

- SNI: для `youtube.com`/`ytimg.com` — верхний регистр имени; для
  `*.googlevideo.com` — подмена на `www.google.com`, реальный `Host`.
- Bootstrap `GET https://www.youtube.com/` — только для ключа и
  `visitorData`; при неудаче — публичный ключ и локальный visitor.
- `net::closeIdleConnections()` перед стартом видео обязателен.

### 7.2. Бюджет SSL

- Всего 4 сессии libnx `ssl`.
- UI: 2 keep-alive (API + картинки), но **динамически**: не больше 2 живых
  одновременно; при нехватке — закрывать простаивающие.
- Плеер: 2 сессии (видео + аудио), резервируются заранее.
- Ретранслятор: 4 слота, но каждый слот — это исходящий TCP; SSL-сессии
  расходуются только там, где нужен TLS.
- При исчерпании — очередь с дедлайном, а не «все слоты» в штатном сценарии.

### 7.3. InnerTube

- `browse`/`search`/`next`: `ANDROID_VR 1.62.27`, `X-YouTube-Client-Name: 28`.
- `/player`: `ANDROID 20.10.38`, `X-YouTube-Client-Name: 3`.
- Bootstrap: WEB Chrome 131 UA.
- Обязательные заголовки: `X-Goog-Api-Format-Version: 2`,
  `X-Goog-Visitor-Id` (если есть), `Origin`, `Referer`, `Accept-Language`.
- `User-Agent` не дублировать (`NET-07`).
- Consent-cookie и `SOCS` — по `YT-04`.
- `visitorData` персистентный (`YT-02`), иначе каждая сессия — «новичок».

### 7.4. Обложки

- Сейчас: `404` на `hqdefault.jpg`. Проверить хост, путь, `Referer`,
  размеры (`hqdefault`, `mqdefault`, `sddefault`, `maxresdefault`).
- `404` допустим для отсутствующего размера — это не ошибка сети;
  переход к следующему размеру, затем placeholder.
- Placeholder — тональный прямоугольник `surfaceContainerHigh` с иконкой
  `image`, без «битой» картинки.
- Кэш: ≤ 24 МБ, LRU, ключ — URL без query-токенов (`RD-05`).

### 7.5. Диагностический билд (обязателен)

Собрать `TubeNX-diag.nro` (флаг `-DTNX_DIAG=1`) и снять лог на консоли.
В лог добавить:

1. Версия, режим (dock/handheld), IP, шлюз, DNS.
2. Для каждого запроса: метод, схема+хост+путь (без query), версия HTTP,
   факт переиспользования соединения, время до connect/TLS/first byte/total,
   размер, код.
3. Первые 300 байт тела при `4xx/5xx` (экранировать, без токенов).
4. Полные отправленные заголовки (кроме cookie/authorization) — один раз
   на хост.
5. TLS: версия, cipher, ALPN, SNI, результат проверки цепочки, но **не**
   каждое `WOULD_BLOCK`.
6. SOCKS: этапы (connect, method, auth, request, reply), тайминги.
7. Ретранслятор: слот, upstream-код, байты, время, Range.

Формат строк — §11.2. Лог — `sdmc:/switch/TubeNX/logs/`.

### 7.6. Гипотезы и порядок их исключения

| Гипотеза | Как проверить | Признак подтверждения |
|---|---|---|
| H1. Заголовки/HTTP-версия → `400` | Повторить `GET /` с минимальным набором заголовков и с `HTTP/1.1` | `400` исчезает при смене набора |
| H2. Переиспользование соединения |Отключить keep-alive для bootstrap | `400` только на втором запросе |
| H3. SNI-подмена ломает bootstrap | Запрос без подмены SNI | `400` исчезает |
| H4. `404` обложек — неверный хост/путь | Сравнить фактический URL с эталоном браузера | путь отличается |
| H5. `404` — регион/consent | Запрос с `Referer: https://www.youtube.com/` и cookie | `200` |
| H6. 3 КБ/с — блокирующий relay | Замер на прямом SOCKS без ретранслятора | скорость растёт |
| H7. 3 КБ/с — размер буфера/`poll` | Увеличить буферы, убрать `poll` на 5000 мс | скорость растёт |
| H8. 3 КБ/с — провайдер | Тот же URL с ПК через тот же SOCKS | на ПК быстро → не провайдер |

Правило: **одна причина — один фикс** (`refactor-tz` §4.3). Каждая гипотеза
закрывается логом до/после, а не рассуждением.

### 7.7. Приёмка сети

- [ ] `GET https://www.youtube.com/` → `200` **или** документированный
      fallback, который грузит ленту.
- [ ] `POST /youtubei/v1/browse` → `200` за < 20 с на нормальном Wi-Fi.
- [ ] Обложки ≥ 90 % `200`, остальные — placeholder.
- [ ] Нет `curl 7`.
- [ ] Нет «все слоты» в штатном сценарии.
- [ ] `SetSocketDescriptor` не логируется как ошибка при успехе.
- [ ] ≤ 10 строк TLS-лога на 10 рукопожатий.
- [ ] В логе нет литерала `%lld`.
- [ ] Ретранслятор: ≥ 2 МБ/с на локальном тесте, Range `206`.

## 8. DPI, SOCKS5 и ретранслятор

- Фрагментация ClientHello: 1-й фрагмент 1 байт (2 байта на этой сети
  ломаются), далее по режиму; пауза 1 мс; без RST.
- Режимы: `Split`, `MultiSplit`, `SplitDisorder`, `TlsRecordSplit`;
  автовыбор (`DPI-06`) по результату probe, а не по названию.
- SNI-подмена только для целей, где она нужна; для остальных — реальный SNI.
- Ретранслятор: `GET /u?u=…`, `HEAD`, `Range`, `206`, `416`, `Content-Range`,
  корректный `pctDecode`, лимит URL, отказ при пустом `u`, `Connection:
  keep-alive`, таймауты, 4 слота, `/healthz` с JSON.
- Ошибки ретранслятора — человекочитаемые коды в теле, детали в лог.
- Локальность: слушать только `127.0.0.1`, случайный порт при занятом 8899,
  никакой авторизации извне.
- Жизненный цикл потоков: один старт/стоп, без гонок, `pthread_join`,
  закрытие fd, `SIGPIPE` игнорируется.
- Host-паритет: тот же код собирается под Linux (`-DTNX_HOST`) и проходит
  тесты SOCKS/relay.

## 9. Плеер

### 9.1. Конфигурация mpv

- `vo=libmpv`, `ao=audren,hos,sdl,null`, `hwdec=no` (или безопасный),
  `cache=yes`, `cache-secs`, `demuxer-max-bytes`, `audio-file-auto=no`.
- `ytdl=no`, `config=no`, сеть только через ретранслятор.
- Видео и аудио — отдельными `loadfile`/`audio-add`; аудио добавляется
  после `FILE_LOADED`.
- `audio-delay` — из конфига; применяется без перезапуска.

### 9.2. Выбор потоков

- Приоритет: 720p (136) + AAC (140) → 480p/360p → muxed 18.
- 1080p штрафуется (декодер/память), VP9/AV1 штрафуются.
- Выбор детерминированный: при равных баллах — меньший itag.
- Истёкшие ссылки (`403`/`410`) → повторный `/player` и переселект
  (`YT-08`, `PLR-05`).

### 9.3. Поведение

- Открытие: `streams:` в лог → `file-loaded` → `video-params` → `audio-params`.
- 60 секунд непрерывно, звук есть; пауза/продолжение; seek ±30 с;
  выход и повторный вход; нет вечного «Буферизация…».
- Seek: не чаще 1 раза в 200 мс, игнор до `FILE_LOADED`, защита от stale
  `FILE_LOADED`, прогресс из `time-pos`.
- Завершение: `ended` → кнопка «Смотреть снова» + «Похожие» (если есть).
- Ошибки: карточка §5.7, «Повторить» перезапрашивает `/player`.
- Выход: `close()` освобождает mpv, аудио, рендер-буфер; повторный вход
  работает; утечек нет.

## 10. Конфиг и история

### 10.1. Файлы

- `sdmc:/config/TubeNX/config.ini` — ключ=значение, UTF-8, без переводов
  строк в значениях.
- `sdmc:/config/TubeNX/history.tsv` — TSV, версия схемы в первой строке.
- `sdmc:/config/TubeNX/state.json` — `visitorData`, last-good IP, флаги
  первого запуска.

### 10.2. Схема

Ввести `schema=2` (или явный `version=2`) и миграции:

1. Чтение: если версии нет — считать v1, смигрировать, записать v2.
2. Валидация каждого поля: диапазоны (`quality 0..3`, `speed 50..200`,
   `audioDelay −2000..2000`, `dpiMode 0..3`), прокси — парсер `UX-09`.
3. Неизвестные ключи сохраняются, а не теряются.
4. Битый файл → бэкап `.bak` и значения по умолчанию, в лог.

### 10.3. Запись

- Атомарно: `config.ini.tmp` → `fsync` → `rename`. То же для истории.
- Не писать на каждое изменение: debounce 500 мс + запись на выходе/сне.
- Ошибка записи — в лог, UI не падает.

### 10.4. История

- Лимит: 200 записей (единый для чтения и записи).
- Поля: `id`, `title`, `channel`, `time`, `duration`, `watchedAt`, `liked`,
  `schema`.
- «Продолжить просмотр»: только `30 с < time < 95 %`; завершённые не
  показывать (`UX-10`).
- Сохранение позиции раз в 5 с, на паузе, на выходе, на сне.
- «Очистить историю» — с диалогом, удаляет файл и состояние в памяти.
- «Убрать» отдельную запись — из меню/фокуса.
- Никакой отправки истории наружу.

### 10.5. Первый запуск

- `firstRun=true` → Splash с онбордингом: «Обход DPI включён»,
  «Проверить соединение», опционально «Указать прокси», «Продолжить».
- Проходится за ≤ 2 нажатия; сеть не блокирует.

## 11. Логи и наблюдаемость

### 11.1. Уровни

`ERROR`, `WARN`, `INFO`, `DEBUG` (только diag-билд). В релизе — `INFO`.
Переключение — конфиг + экран диагностики.

### 11.2. Формат

```
<uptime_ms> <level> <domain>: <сообщение> [key=value ...]
```

Домены: `net`, `dpi`, `socks`, `relay`, `yt`, `player`, `cfg`, `ui`,
`display`, `life`.

Обязательные маркеры (по ним проверяют приёмку):

| Маркер | Когда |
|---|---|
| `net: GET https://www.youtube.com/ -> 200` | bootstrap |
| `yt: browse ok items=… ms=…` | лента |
| `yt: streams itag=136 audio=140` | выбор потоков |
| `player: file-loaded` | файл открыт |
| `player: video-params 1280x720` | видео пошло |
| `player: audio-params aac` | звук пошёл |
| `player: ended` | конец |
| `dpi: mode=split frag=1` | обход включён |
| `relay: slot=1 range=0- status=206` | ретранслятор |
| `display: dock 1920x1080 scale=1.5` | режим |

### 11.3. Правила

- Никаких литералов форматирования (`%lld`) в тексте лога.
- Rate limit: одинаковое сообщение — не чаще 1 раза в 500 мс, с
  `(повторено N раз)`.
- `WOULD_BLOCK` — не `ERROR`, а `DEBUG`.
- Токены, cookie, подписанные query — вырезать.
- Файл: `sdmc:/switch/TubeNX/logs/tubenx-YYYYMMDD-HHMMSS.log`, ротация
  по 2 МБ, хранить 3 файла.
- Crash-лог: последние 200 строк + причина (`PL-08`).

## 12. Производительность

- 60 fps в UI (30 допустимо в тяжёлых сценах), без busy-wait.
- Бюджет кадра: ≤ 16 мс на 1280×720; dock 1080p — ≤ 16 мс с масштабом.
- Память: пик ≤ 512 МБ (с mpv и 4 слотами); без монотонного роста.
- Кэш глифов ≤ 8 МБ, LRU; кэш картинок ≤ 24 МБ, LRU.
- Частичная перерисовка: статичные слои (app bar, чипы) не перерисовываются
  при скролле.
- Не рисовать полноэкранные градиенты каждый кадр; скримы — в слое плеера.
- Один blit кадра видео, без лишних аллокаций (`RD-10`).
- Выход из приложения < 2 с; shutdown идемпотентен.

## Приложение D. Глоссарий

- **itag** — числовой идентификатор формата YouTube.
- **InnerTube** — внутренний API YouTube.
- **SNI** — имя сервера в TLS ClientHello.
- **DPI** — глубокий анализ трафика у провайдера.
- **relay** — локальный HTTP-ретранслятор для mpv.
- **safe area** — зона, гарантированно видимая на ТВ.
- **NACP** — метаданные приложения для hbmenu.
