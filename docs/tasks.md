# Задачи TubeNX

Список задач для двух новых участников: зоны, критерии приёмки и порядок,
в котором их удобно брать. Источник правды по статусу — манифест
`handoff/deepseek/manifest.json` (внутренний, в публичную ветку не входит);
здесь — то, что можно брать руками.

Перед первой задачей прочитай [`CONTRIBUTING.md`](../CONTRIBUTING.md) и
[`docs/onboarding.md`](onboarding.md).

---

## 1. Зоны

| Зона | Кто | Каталоги и файлы | Что можно делать |
|---|---|---|---|
| **A. Интерфейс** | участник 1 | `source/ui/`, `source/md3/`, `source/core/`, `tools/` (кроме защищённых), `docs/`, `resources/` | экраны, виджеты, тема, рендер, тексты, документация |
| **B. Сеть и плеер** | участник 2 | `source/net/`, `source/dpi/`, `source/yt/`, `source/player/` | HTTP, SOCKS/DPI, InnerTube, libmpv |
| **D. Дизайн** | дизайнер | `design/` | макеты, токены, PNG, иконка; `source/` не трогать |
| **Общая** | только по согласованию | `source/main.cpp`, `source/platform.hpp`, `Makefile` (кроме `ICON`), `.github/*` | главный цикл, платформа, сборка, CI |

`design/` — read-only для разработчиков и зона дизайнера одновременно:
дизайнер меняет её отдельной веткой по согласованию, разработчик не правит
макеты вообще. Правила — [`docs/design-guide.md`](design-guide.md).

Защищённые файлы, которые нельзя править без явного согласования:
`tools/test_host.sh`, `tools/doctor.sh`, `tools/deploy.sh`, `tools/pull-log.sh`,
`tools/test_theme.cpp`, `tools/test_net.cpp`, `tools/test_dpi.cpp`.

Правило простое: **один файл в один момент времени — один человек**. Если
задача требует файла из чужой зоны, сначала договоритесь, потом правьте.

## 2. Определение готовности (DoD)

Задача считается сделанной, когда выполнено всё:

- [ ] код собирается: `make -j$(nproc)` и `make diag` — **0 предупреждений**;
- [ ] `make test-host` — `== ИТОГ: ЗЕЛЁНО ==`;
- [ ] для новой логики есть host-тест; для UI — `tools/preview.sh` без регрессий;
- [ ] для дизайна — `node design/tools/wd.mjs audit` разобран, PNG
      перерендерены, токены не правились руками;
- [ ] нет новых зависимостей и портлиб без обсуждения;
- [ ] нет секретов, cookie, личных IP, серийников и локальных путей в коде,
      логах и документации;
- [ ] комментарии и логи — по-русски, по делу;
- [ ] обновлён `CHANGELOG.md`, если изменение видно пользователю;
- [ ] в PR указан номер задачи и написано, **как проверял**;
- [ ] если пункт требует железа — в PR написано «ждёт консоли», а не «готово».

Отдельно: `design/` не трогаем, `docs/impl-tz.md` важнее комментариев в коде.

## 3. Как взять задачу

1. Выбери задачу из раздела 4 или 5.
2. Напиши в issue/чат: «беру `PL-07`», чтобы её не взял второй.
3. Создай ветку: `git switch -c имя/pl-07-error-screens`.
4. Делай маленькими коммитами, формат — в `CONTRIBUTING.md`.
5. Открой PR (можно draft сразу) и опиши: что, зачем, как проверял, риски.
6. Если задача требует консоли — договорись с владельцем консоли о прогоне.

Если задача кажется большой — разбей на две и напиши об этом в PR.

## 4. Первые задачи без консоли

Это стартовый набор: не требуют Switch, не пересекаются между собой и дают
понятный результат. Бери по одной.

### A-1. `DOC-01` — проверить онбординг «с нуля» (зона A, самая простая)

**Что:** пройти [`docs/onboarding.md`](onboarding.md) на чистой машине или в
контейнере: установка devkitPro, `make doctor`, `make -j`, `make test-host`,
`preview.sh`. Найти неточности и исправить.

**Приёмка:**
- все команды из документа выполнены, вывод совпал с описанным;
- каждая неточность исправлена отдельным коммитом;
- в документе нет локальных путей и личных данных;
- PR содержит список «что не сошлось».

**Файлы:** `docs/onboarding.md`, при необходимости `tools/toolchain.md`.

---

### A-2. `PL-07` — экраны ошибок «нет SD / нет сети / нет romfs» (зона A)

**Что:** сейчас ошибки только логируются. Нужны три понятных состояния с
человеческим текстом и кнопкой «Повторить»:

| Состояние | Когда | Что показать |
|---|---|---|
| Нет SD | `sdmc:` не смонтирована или read-only | «SD-карта недоступна» + как исправить; приложение не падает |
| Нет сети | Wi-Fi не подключён / `curl` не стартует | «Нет подключения к сети» + «Повторить» |
| Нет romfs | не найдены ресурсы (шрифты/иконка) | «Повреждена установка» + куда переустановить |

**Приёмка:**
- три состояния можно увидеть в `preview` (добавь параметр состояния в
  `tools/preview.cpp` или отдельный маленький генератор);
- тексты без кодов `curl`, `errno` и английских простыней;
- кнопка «Повторить» реально повторяет операцию, а не перезапускает приложение;
- нет правок в `main.cpp` (если нужен hook — согласуй).

**Файлы:** `source/ui/screens.cpp`, `source/ui/app.cpp`, `source/ui/strings.hpp`,
`tools/preview.cpp`.

---

### A-3. `RD-01` — частичная перерисовка (dirtyRect) (зона A, сложнее)

**Что:** сейчас flush в framebuffer идёт построчно с эвристикой на полную
копию. Нужен dirty-rect: экран сообщает, какая область изменилась, кадр
копируется только туда.

**Приёмка:**
- на статичном экране (главная без анимаций) объём копирования падает
  заметно — измерь `perf: rows=` и `drawn=` до/после;
- скролл, фокус, ripple, открытие диалога не оставляют артефактов;
- `preview` совпадает с эталоном пиксель-в-пиксель (или отличия объяснены);
- host-тест на пересечение прямоугольников и объединение dirty-областей.

**Файлы:** `source/core/canvas.*`, `source/ui/app.cpp`, `source/ui/screens.cpp`,
`tools/test_canvas.cpp` (можно расширять).

---

### A-4. `PL-08` — `std::set_terminate` и экран ошибки (зона A + `main.cpp` по согласованию)

**Что:** перехват сигналов и `crash.log` уже есть. Не хватает
`std::set_terminate` (необработанное исключение/`std::terminate`) и экрана
«Произошла ошибка» с кодом при следующем запуске.

**Приёмка:**
- в diag-сборке `abort()` и `throw` (там, где исключения разрешены) дают
  `crash.log` с сигналом и хвостом ring-буфера;
- при следующем запуске показывается экран с кодом и кнопкой «Продолжить»;
- обычная сборка не меняет поведение;
- флаг `crash-test` работает как раньше.

**Файлы:** `source/ui/app.cpp`, `source/core/*`, `source/main.cpp` — только
после согласования.

### A-5. `PL-05` — лог кучи после init/Home/Player (зона A)

**Что:** добавить `heap:` в лог через `mallinfo2()` в трёх точках: после
инициализации, после загрузки главной, после открытия плеера. Нужно, чтобы
ловить утечки по 10-минутному прогону.

**Приёмка:**
- строки `heap: stage=init used=… free=…` в boot-логе;
- функция не ломает сборку без `malloc.h` (проверь `#ifdef`);
- есть host-тест форматирования строки;
- 10-минутный замер на консоли — отдельным пунктом, «ждёт консоли».

**Файлы:** `source/ui/app.cpp`, `source/core/*`, `source/platform.hpp` — по
согласованию.

### B-1. `TEST-08` + `SEC-07` — фаззеры JSON/URL (зона B)

**Что:** DPI-парсеры уже фаззятся, а JSON InnerTube и URL/Range — нет. Нужны
цели libFuzzer для `yt/innertube` (разбор ответа) и `net/http` (URL, `Range`,
заголовки).

**Приёмка:**
- `tools/fuzz_json.cpp`, `tools/fuzz_url.cpp`, `tools/fuzz.sh` (clang,
  `-fsanitize=fuzzer,address`);
- 1 000 000 прогонов на каждый без падений и утечек;
- найденные падения исправлены с host-тестом-регрессией;
- запуск описан в `CONTRIBUTING.md`; CI не требуется.

**Файлы:** `tools/fuzz_*`, `source/yt/innertube.cpp` (только если найден баг),
`source/net/http.cpp` (то же).

---

### B-2. `PL-04` — рефкаунт CPU boost вокруг `open()` (зона B)

**Что:** сейчас всегда `ApmCpuBoostMode_Normal`. Нужен `setBoost(true/false)`
с рефкаунтом: boost включается на открытие потока и первые ~10 секунд, затем
снимается; вложенные вызовы не сбрасывают его раньше времени.

**Приёмка:**
- логи `boost: 1→2`, `boost: 2→1`, `boost: off`;
- boost гарантированно снимается при ошибке открытия, выходе и сне;
- host-тест на рефкаунт (вынеси счётчик в тестируемую функцию);
- 30 минут видео на консоли без троттлинга — «ждёт консоли».

**Файлы:** `source/player/player.cpp`, `source/player/player.hpp`.

---

### B-3. `DPI-12` — 10 параллельных клиентов relay (зона B)

**Что:** при заполненных слотах relay отвечает `503` + `Retry-After: 1` и
закрывает соединение без RST. Нужен host-тест на 10 одновременных клиентов
против живого локального ретранслятора.

**Приёмка:**
- 10 потоков: часть получает поток, часть — корректный `503`;
- счётчик `errors` не растёт от ожидаемого `503`;
- нет RST и зависших сокетов после теста;
- тест не флакает при 20 повторных запусках.

**Файлы:** новый `tools/test_relay_parallel.cpp` (не трогай `tools/test_dpi.cpp`),
`source/dpi/dpi.cpp` — только если найден баг.

---

### B-4. `PLR-11` — восстановление аудио после сна (зона B)

**Что:** после `OnResume` аудио-дорожка переустанавливается, но нет проверки,
что AO реально ожил, и нет перезапуска потока при отказе.

**Приёмка:**
- после пробуждения проверяется состояние AO; при мёртвом — перезапуск
  аудио-потока с текущей позиции;
- лог `audio: wake ok` / `audio: wake failed -> restart`;
- если перезапуск невозможен — понятное сообщение, а не тишина;
- финальная проверка «сон 30 с → видео продолжается» — на консоли.

**Файлы:** `source/player/player.cpp`, `source/ui/app.cpp` (хук уже есть).

### D-1. `DESIGN-01` — ревизия макета и экспорта (зона D, без консоли)

**Что:** пройти все доски, перерендерить PNG и разобрать аудит. Цель — чтобы
`design/` и `design/png/` совпадали, а механические дефекты были исправлены.

**Приёмка:**
- для каждой страницы выполнен `wd.mjs frames`, `shoot`, `audit`;
- реальные дефекты (кегль < 12, иконка вне сабсета, выход за фрейм,
  обрезка без многоточия, контраст) исправлены;
- шум аудита (disabled 0.38, тени всплывающих, пустые `<i>`) отмечен в отчёте;
- PNG в `design/png/` перерендерены и совпадают с разметкой;
- `docs/m3-matrix.md` обновлён, если найден новый компонент/состояние;
- в PR нет правок `source/` и чужих страниц «заодно».

**Файлы:** `design/screens/`, `design/png/`, точечно `design/assets/` — только
по согласованию.

### D-2. `DESIGN-02` — новый экран или состояние (зона D, по запросу)

**Что:** когда в приложении появляется новая функция или не хватает состояния
(пусто/ошибка/загрузка/фокус), дизайнер рисует фрейм по ТЗ и передаёт его в
код. Конкретный экран выдаёт владелец — не выдумывай функции, которых нет.

**Приёмка:**
- фрейм 1280×720 (TV — 1920×1080) с уникальным `id`, `.name` и `.spec`;
- тёмная тема, для Home/Settings — ещё светлая;
- все состояния: норма, загрузка, пусто, ошибка, фокус;
- тексты по `docs/design-tz.md` §7, контраст ≥ 4.5:1;
- `wd.mjs audit` разобран, PNG отрендерен и просмотрен глазами;
- в PR — таблица «id → что это» и что именно проверено.

**Файлы:** `design/screens/`, `design/png/`, `design/export/`.

## 5. Задачи, которым нужна консоль

Их можно брать, только если есть доступ к Switch и договорённость с владельцем
консоли. Кодовая часть делается заранее, приёмка — по логу.

| Задача | Что проверить | Строки в логе |
|---|---|---|

| `DPI-12` | 10 параллельных клиентов на живом relay | `relay: слоты`, `503` |
| `PERF-01` | p95 кадра по экранам | `perf: upd/draw/p95` |

| `PERF-07` | загрузка CPU при 720p | `player metrics`, `perf:` |

Шаблон отчёта и порядок шагов — [`docs/hardware-smoke.md`](hardware-smoke.md).

## 7. Как распределить между участниками

Если вас трое (UI, сеть/плеер, дизайн) и консоли нет:

| Неделя | Участник 1 (UI/M3) | Участник 2 (сеть/плеер) | Дизайнер |
|---|---|---|---|
| 1 | `DOC-01`, затем `PL-07` | `TEST-08`/`SEC-07` | `DESIGN-01` |
| 2 | `RD-01` (dirtyRect) | `PL-04` (boost) | `DESIGN-02` по запросу |
| 3 | `PL-08` (terminate + экран) | `DPI-12` (параллельные клиенты) | новые состояния для текущих задач |
| 4 | `PL-05` (лог кучи) | `PLR-11` (аудио после сна) | ревизия TV/светлой темы |

Владелец консоли в это время прогоняет `docs/hardware-smoke.md` и принимает
задачи, помеченные «ждёт консоли».

Как получить доступ и зону — [`docs/coauthorship.md`](coauthorship.md); как
работать с макетами — [`docs/design-guide.md`](design-guide.md).

## 9. Шаблон PR

```
PL-07: экран «SD-карта недоступна»

Что сделано:
- ...

Зачем:
- ...

Как проверял:
- make -j$(nproc): 0 предупреждений
- make test-host: ЗЕЛЕНО
- preview: 08_no_sd.png, регрессий нет
- на консоли: не проверял (нужна SD)

Риски:
- ...
```

Чем честнее PR, тем быстрее ревью. «Не проверял» — нормальный ответ;
«должно работать» — нет.
